---
title: Choose a school and settings
description: Pick an ayanamsa and house system, set them once, and keep KP and Parashari results apart.
---


Every calculation depends on two settings, the **ayanamsa** and the **house
system**, together called **AstroParams**. Choose them, set them in code or
from the environment, and check which ones a result used.

## Presets

| You want | Ayanamsa | House system | School |
| --- | --- | --- | --- |
| KP readings, using cusps, star lords, sub lords, and significators | `KrishnamurtiVP291` | `Placidus` | KP |
| Parashari readings, using signs and divisional charts | `Lahiri` | `WholeSign` | Parashari |
| No preference | Leave the defaults | | KP |

The defaults are `KrishnamurtiVP291` with `Placidus`: set nothing and you work
in the KP school. Never mix the two schools in one judgment. To offer both, run
each with its own settings, as in [Both schools](#both-schools).

## Ayanamsa and house system

The **ayanamsa** is the offset that aligns tropical longitudes with the fixed
sidereal zodiac. It changes every longitude Ascendant reports, for the Lagna
and each graha.

The **house system** places the twelve house cusps of the **D1** chart. It
affects D1 only. Divisional charts always use whole-sign houses counted from
their mapped Lagna, under any house system.

AstroParams are not part of the birth moment. They are settings of the
calculation, and every chart calculation records the ones it used.

## Set in code

Pass the settings to `AstroParams.layer` when you build the runtime.

```ts
import { AstroParams, Swisseph } from "astro-ascendant";
import { Layer, ManagedRuntime } from "effect";

const runtime = ManagedRuntime.make(
  Layer.mergeAll(
    AstroParams.layer({ ayanamsa: "Lahiri", houseSystem: "WholeSign" }),
    Swisseph.SwissephCachedLayer,
  ),
);
```

`AstroParams.layer` takes an `Options` value, so TypeScript rejects unknown
ayanamsa and house-system names. `AstroParams.DefaultAstroParams` holds the
defaults that `Runtime.MainLayer` uses.

## Effect on results

One birth, `2000-01-01 12:00 UTC` at `12.9716° N`, `77.5946° E`, under both
presets:

| Result | `KrishnamurtiVP291` + `Placidus` | `Lahiri` + `WholeSign` |
| --- | --- | --- |
| Lagna longitude | 69.684° | 69.607° |
| Lagna sign | Gemini | Gemini |
| House 2 cusp in D1 | 95.392° | 90.000° |

The ayanamsa moves the Lagna by a fraction of a degree, enough to change a
star, a sub lord, or a sign at a boundary. The house system moves the cusps.
Whole-sign houses always begin at a multiple of 30°; Placidus cusps do not.

### House systems

Ascendant supports 13 house systems. `Placidus` is the default.

| Name | How it divides the houses |
| --- | --- |
| `Placidus` | By time. Unequal houses. The default. |
| `WholeSign` | One sign per house. The Lagna's sign is house 1, and every house is 30°. |
| `Koch` | By time, from the birthplace meridian. Unequal houses. |
| `Equal` | Twelve 30° houses counted from the Lagna's exact degree. |
| `VehlowEqual` | Equal 30° houses with the Lagna in the middle of house 1. |
| `Porphyrius` | Each quadrant between the angles in three equal parts. |
| `Regiomontanus` | A medieval system based on divisions of the celestial equator. |
| `Campanus` | Based on divisions of the prime vertical. |
| `Meridian` | Axial rotation: equal in time, measured from the meridian. |
| `Morinus` | Based on the celestial equator, with equal 30° houses. |
| `Alcabitus` | A medieval Arabic system. |
| `PolichPage` | Topocentric: a modern time-based system close to Placidus. |
| `Azimuthal` | Based on the horizon. For specialized use. |

<Callout type="warn" title="High latitudes">
  Placidus and Koch are undefined inside the polar circles, where some degrees
  never rise or set. There, `Chart.generate` fails with a
  `ChartCalculationError` instead of returning bad cusps. In a test, 66° N
  worked and 68° N failed. Other systems, such as `Equal`, `WholeSign`, and
  `Campanus`, still return cusps, but they are not meaningful near the poles.
  For births far north or south, choose the house system deliberately.
</Callout>

## Both schools

Build one runtime per school and send each judgment to the matching one, so KP
and Parashari results never mix.

```ts
import { AstroParams, Swisseph } from "astro-ascendant";
import { Layer, ManagedRuntime } from "effect";

export const kp = ManagedRuntime.make(
  Layer.mergeAll(
    AstroParams.layer({ ayanamsa: "KrishnamurtiVP291", houseSystem: "Placidus" }),
    Swisseph.SwissephCachedLayer,
  ),
);

export const parashari = ManagedRuntime.make(
  Layer.mergeAll(
    AstroParams.layer({ ayanamsa: "Lahiri", houseSystem: "WholeSign" }),
    Swisseph.SwissephCachedLayer,
  ),
);
```

Run each calculation on the runtime that matches the question, for example
`kp.runPromise(Chart.generate(located))`. Dispose both at shutdown.

## Environment variables

`AstroParams.layerConfig` reads the settings from Effect `Config`, so each
deployment can choose them without code changes.

```ts
import { AstroParams, Swisseph } from "astro-ascendant";
import { Config, Layer, ManagedRuntime } from "effect";

const settings = AstroParams.layerConfig({
  ayanamsa: Config.schema(AstroParams.Ayanamsa, "AYANAMSA"),
  houseSystem: Config.schema(AstroParams.HouseSystem, "HOUSE_SYSTEM"),
});

const runtime = ManagedRuntime.make(
  Layer.mergeAll(settings, Swisseph.SwissephCachedLayer),
);
```

Run it with the variables set:

```bash
AYANAMSA=Raman HOUSE_SYSTEM=Equal bun run app.ts
```

An unknown name, such as `AYANAMSA=Nope`, fails the program with a
`ConfigError` listing the accepted values. The app stops at startup instead of
producing a chart with the wrong settings.

## Recorded settings

Each chart calculation carries the settings it used:

```ts
const calculation = yield* Chart.generate(located);

console.log(calculation.astroParams);
// { ayanamsa: "Lahiri", houseSystem: "WholeSign" }
```

Store or display this with every result. A reading is repeatable only if you
can name the ayanamsa and house system behind it.
