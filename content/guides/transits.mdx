A **transit search** finds when one graha does something specific: enters a
sign, reaches a longitude, crosses a house cusp, or turns around. You give a
starting **Located Moment**, and the search returns the next or previous events in
time order. It reports exact moments and nothing else. There is no
interpretation in the result.

`Transit.findTransits` is the module's only function. This guide runs a first
search, explains every request field and event kind, and covers the two things
you must know about in version 6.0.0.

## Run a first search

Find the next three sign ingresses of Jupiter after 1 November 2026:

```ts
import { Chart, Runtime, Transit } from "astro-ascendant";
import { DateTime, ManagedRuntime } from "effect";

const runtime = ManagedRuntime.make(Runtime.MainLayer);

const from = Chart.LocatedMoment.make({
  moment: Chart.Moment.make({ date: DateTime.makeUnsafe("2026-11-01T00:00:00Z") }),
  latitude: 12.9716,
  longitude: 77.5946,
});

const events = await runtime.runPromise(
  Transit.findTransits({
    planet: "Jupiter",
    from,
    count: 3,
    direction: "forward",
    kinds: ["sign-ingress"],
    maxYears: 12,
  }),
);
```

Each event reports where and when:

| Moment (UTC) | Longitude | Sign | Retrograde |
| --- | --- | --- | --- |
| 2027-01-25 11:30 | 120° | Cancer | yes |
| 2027-06-25 13:09 | 120° | Leo | no |
| 2027-11-25 23:14 | 150° | Virgo | no |

The first event is Jupiter moving backward across the Cancer and Leo boundary
while retrograde. The search counts **every** crossing in strict time order, so a
retrograde sweep produces extra events and a boundary can appear three times.

An event's `sign` is the sign the graha moves into at that instant, in the
direction of the search. Here Jupiter moves back into Cancer, then forward into
Leo, then Virgo.

## The request

| Field | Meaning |
| --- | --- |
| `planet` | The graha to follow. Any of the nine, Rahu and Ketu included. |
| `from` | The Located Moment to search from. Its location is used for house cusps and attached charts. |
| `count` | How many events to return, from 1 to 100. |
| `direction` | `"forward"` for the next events, `"backward"` for the previous ones. |
| `kinds` | One or more event kinds, listed below. At least one is required. |
| `targetLongitude` | Required with `longitude-hit`. |
| `house` | Required with `cusp-crossing`, from 1 to 12. |
| `maxYears` | How far to search, up to 200. The default is 30. |
| `precisionMinutes` | How precisely each moment is refined. The default is 1 minute. |
| `includeCharts` | Divisions to attach to every event. See [Attach charts](#attach-charts). |

To search into the past, set `direction: "backward"`. The events then come back
newest first. From 1 November 2026, Jupiter's previous two ingresses were into
Cancer at 2026-10-30 15:40 UTC and into Gemini at 2026-06-01 10:36 UTC.

## Event kinds

| Kind | The event | Needs |
| --- | --- | --- |
| `sign-ingress` | The graha crosses a sidereal sign boundary, at a multiple of 30°. | Nothing |
| `longitude-hit` | The graha reaches an exact longitude. | `targetLongitude` |
| `cusp-crossing` | The graha crosses the cusp of a house, as that cusp stands at `from`. | `house` |
| `station` | The graha stops and reverses direction. | Nothing |

You can list several kinds in one search. A missing field fails with a typed
`TransitValidationError`, for example `targetLongitude is required for
longitude-hit searches`.

### Sign ingress

This is the search from the first example. It needs no extra fields and returns
the sign entered.

### Longitude hit

Pass the longitude you want in `targetLongitude`:

```ts
const events = await runtime.runPromise(
  Transit.findTransits({
    planet: "Saturn",
    from,
    count: 2,
    direction: "forward",
    kinds: ["longitude-hit"],
    targetLongitude: Chart.Longitude.make(350),
  }),
);
```

<Callout type="warn" title="Known issue in 6.0.0: opposite-point results">
  In version 6.0.0, `longitude-hit` and `cusp-crossing` also return the moments
  when the graha reaches the point exactly **opposite** the target, 180° away.
  Searching the Sun for 100° returns 100° in July and 280° in January, alternately.
  `sign-ingress` and `station` are not affected.

  Until this is fixed, keep only the events whose longitude is near your target,
  and ask for twice as many as you need:

  ```ts
  const circularGap = (a: number, b: number) => {
    const gap = Math.abs(a - b) % 360;
    return Math.min(gap, 360 - gap);
  };

  const target = 100;
  const events = await runtime.runPromise(
    Transit.findTransits({
      planet: "Sun",
      from,
      count: 8, // twice the 4 hits wanted
      direction: "forward",
      kinds: ["longitude-hit"],
      targetLongitude: Chart.Longitude.make(target),
    }),
  );
  const hits = events.filter((event) => circularGap(Number(event.longitude), target) < 1);
  // 4 events: 2027-07-27, 2028-07-26, 2029-07-26, 2030-07-27
  ```
</Callout>

### Cusp crossing

Name the house, and the search follows the cusp of that house as it stands in the D1
chart at `from`:

```ts
const events = await runtime.runPromise(
  Transit.findTransits({
    planet: "Sun",
    from,
    count: 2,
    direction: "forward",
    kinds: ["cusp-crossing"],
    house: 10,
  }),
);
```

The cusp comes from the house system in your settings, so a different house system
gives a different cusp and different crossing times. For the birth location
above, the tenth cusp is at 91.749°, so the real crossing is on 2027-07-18, in
Cancer.

The opposite-point issue above applies here too. The same search also returns
2027-01-16, at 271.749°, and the filter from the callout removes it:

```ts
const { charts } = await runtime.runPromise(Chart.generate(from));
const cusp = Number(charts[0].houses[10].cusp); // 91.749
const crossings = events.filter((event) => circularGap(Number(event.longitude), cusp) < 1);
```

### Station

A station is the moment a graha's apparent motion reverses:

```ts
const events = await runtime.runPromise(
  Transit.findTransits({
    planet: "Mercury",
    from,
    count: 4,
    direction: "forward",
    kinds: ["station"],
  }),
);
```

For Mercury from 1 November 2026:

| Moment (UTC) | Longitude | Sign | What happens |
| --- | --- | --- | --- |
| 2026-11-13 15:54 | 190.876° | Libra | Turns direct |
| 2027-02-09 17:35 | 311.819° | Aquarius | Turns retrograde |
| 2027-03-03 12:32 | 296.760° | Capricorn | Turns direct |
| 2027-06-10 18:15 | 72.194° | Gemini | Turns retrograde |

<Callout type="warn" title="Do not rely on is_retrograde at a station">
  At a station the speed is zero, so the event's `is_retrograde` flag, taken from
  the sign of the speed at that instant, is not a reliable guide to which way the
  graha turns. Version 6.0.0 reports `false` for the February 2027 station above,
  even though Mercury turns retrograde there. Work out the turn from the order
  instead. Stations alternate between turning retrograde and turning direct, and the
  longitude falls after a station that turns retrograde.
</Callout>

## Attach charts

Add `includeCharts` to receive a full chart calculation for each event's moment,
at the location in `from`:

```ts
const events = await runtime.runPromise(
  Transit.findTransits({
    planet: "Jupiter",
    from,
    count: 1,
    direction: "forward",
    kinds: ["sign-ingress"],
    maxYears: 12,
    includeCharts: [9],
  }),
);

const calculation = events[0].calculation; // placements, D1 and D9, and the settings used
```

The search resolves the moments first and attaches charts afterward, so it costs
little when you leave `includeCharts` out. D1 is always included.

## When a search cannot finish

The search fails with a typed error rather than returning a short list quietly.

If the window ends before `count` events are found, the error is
`TransitSearchExhausted`. It carries the events it did find and the time it
searched until, so you can keep the partial result:

```ts
import { Effect } from "effect";

const events = await runtime.runPromise(
  Transit.findTransits({
    planet: "Saturn",
    from,
    count: 100,
    direction: "forward",
    kinds: ["sign-ingress"],
    maxYears: 1,
  }).pipe(Effect.catchTag("TransitSearchExhausted", (error) => Effect.succeed(error.found))),
);
// 2 events: Aries and Pisces
```

An invalid or incomplete request fails with `TransitValidationError`. See [Errors
and typed failures](/docs/guides/errors).

## Speed

A search samples the ephemeris thousands of times. `Runtime.MainLayer` already
uses the cached Swiss Ephemeris layer, so repeated and overlapping searches reuse
earlier positions. If you build your own layers, use `Swisseph.SwissephCachedLayer`
and not `Swisseph.SwissephLayer`. See [Ephemeris adapters and
caching](/docs/guides/ephemeris-and-caching).

## Provenance

Each event records its method: school `Ascendant`, method `transit-sample-bisect`,
version 1. The search samples the graha's position at coarse steps and bisects each
bracketed crossing down to `precisionMinutes`.
